## 문제 상황

기존에는 팀장 정보를 두 곳에서 확인할 수 있었습니다.

- `Team.leaderMember`
- `TeamMember.teamRole == LEADER`

처음에는 TeamMember 테이블만 조회해도 팀장을 확인할 수 있다는 점에서
`LEADER` 역할을 유지하는 것이 명확하다고 생각했습니다.

하지만 팀장 위임 기능을 구현하면서 문제가 드러났습니다.

팀장을 A에서 B로 변경하려면 다음 값을 모두 변경해야 했습니다.

- `Team.leaderMember`: A → B
- 기존 팀장 A의 `TeamRole`: LEADER → MEMBER
- 새로운 팀장 B의 `TeamRole`: MEMBER → LEADER

이 중 하나라도 누락되면 서로 다른 데이터를 기준으로 다른 팀장을 가리키는
정합성 문제가 발생할 수 있었습니다.

## 고민

두 가지 방안을 고려했습니다.

1. `Team.leaderMember`와 `TeamRole.LEADER`를 모두 유지
    - TeamMember만 조회해도 역할이 명확함
    - 하지만 모든 팀장 변경 로직에서 두 상태를 항상 동기화해야 함

2. 팀장 정보의 기준을 `Team.leaderMember` 하나로 통일
    - 팀장 정보를 한 곳에서만 관리할 수 있음
    - TeamMember만 봤을 때 팀장 여부를 바로 알 수 없다는 단점이 있음 ( TeamRole.LEADER 를 삭제 )

## 결정

데이터의 명확성보다 정합성 관리와 변경 안정성을 우선하기로 했습니다.

왜냐하면, 지금까지 프로젝트를 리팩토링하면서 모든 정책을 기억해야만 데이터 정합성이 유지되는 구조는 변경에 취약하다는 점을 크게 느꼈습니다.


프로젝트가 커지면서 테이블과 기능이 늘어났고, 특정 기능에서 어떤 데이터를 함께 변경해야 하는지 파악하기 어려워지는 경험도 있었습니다. 

테스트 코드와 기능 명세가 부족했던 점도 원인이었지만, 하나의 사실을 여러 곳에서 관리하는 구조 자체가 복잡성을 키우는 원인이라고 판단했습니다.

따라서 팀장 여부의 단일 기준을 `Team.leaderMember`로 정하고
`TeamRole.LEADER`를 제거했습니다.

`TeamRole`은 이후 다음 역할만 표현합니다.

- MEMBER
- STAFF

즉, LEADER는 TeamRole로 표현하지 않고,
팀장 여부는 Team.leaderMember를 통해 별도로 관리합니다.

TeamRole은 MEMBER와 STAFF처럼 팀 내 일반적인 역할만 표현합니다.

팀 소속 여부는 `TeamMember`,
팀장 여부는 `Team.leaderMember`를 기준으로 판단하도록 책임을 분리했습니다.

## 개선 결과

팀장 위임 로직은 기존의 여러 상태 변경 대신

`team.changeTeamLeader(newLeader)`

와 같이 하나의 상태만 변경하면 되도록 단순해졌습니다.

이를 통해 개발자가 팀장 변경 시 TeamRole 변경을 누락하여
잘못된 상태를 만들 가능성을 줄였습니다.

## 배운 점

동일한 사실인 "누가 팀장인가"를 Team과 TeamMember 두 곳에서 관리하면
조회 관점에서는 편리할 수 있지만,
그만큼 데이터 동기화와 정합성 관리 비용이 발생한다는 것을 경험했습니다.

특히 중요한 도메인 상태는(Leader) 가능한 한 하나의 엔티티에서 관리를하고,
다른 정보는 그 기준에서 파생되도록 설계하는 것이
변경에 더 안전하다는 것을 배웠습니다.
